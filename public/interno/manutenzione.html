Documentazione interna

Aggiornamenti, backup e manutenzione

Come nasce una versione, come arriva alle sale, come si installa da sola, come vengono salvati i dati e dove finisce ogni file. Vale dalla versione 3.8.0 della suite.

Suite 3.8.0 Hub · Rilasci Nessun cron, nessun FTP Ottobre 2026
01 Il quadro completo

Tre attori: il codice (repository GitHub della suite), l'hub (hub.gesthallsuite.it, che conosce tutte le installazioni) e ogni suite installata in una sala. Nessuno dei tre "cerca" niente da solo nel senso di Internet: ogni passaggio è una richiesta precisa.

REPOSITORY (computer / sessione di sviluppo)
  1. si alza GH_VERSION e si scrive il CHANGELOG
  2. php tools/file_attesi.php   → install/file_attesi.json (elenco file + impronte)
  3. php tools/pacchetto.php     → dist/gesthall-suite-3.8.1.zip
              │  (caricato a mano dal superadmin)
              ▼
HUB  hub.gesthallsuite.it
  4. Rilasci → Carica versione → Pubblica   (zip in storage/rilasci/, impronta SHA-256 nel DB)
              ▲  ① una volta al giorno: "sono la sala X, ho la 3.8.0"
              │  ② risposta: "licenza ok, c'è la 3.8.1, impronta abc…"
              │  ③ al clic su Aggiorna ora: download dello zip
SUITE della sala (Impostazioni → Sistema → Aggiornamenti)
  5. backup database → download → controllo impronte → copia dei file vecchi
     → scrittura dei file nuovi → controllo finale
💡

tools/pacchetto.php non trova l'aggiornamento: lo costruisce partendo dai file del repository. Chi "trova" l'aggiornamento è la suite della sala, chiedendo all'hub; l'hub lo conosce perché qualcuno ce l'ha caricato e pubblicato.

02 Creare il pacchetto

Si fa dove c'è una copia del repository della suite e PHP da riga di comando: il proprio computer o una sessione di sviluppo con Claude. Non sul server della sala.

1
Versione e changelog
In includes/lib.php e includes/novita.php si aggiorna GH_VERSION (es. 3.8.1); in docs/CHANGELOG.md si apre la sezione ## [3.8.1]. Il testo per i clienti va nel changelog.json del sito.
2
php tools/file_attesi.php
Prende l'elenco dei file versionati (git ls-files), esclude quelli che non vanno sul server (configurazione, .htaccess principale, documentazione nella radice, tools/, tests/) e per ognuno scrive dimensione e impronta SHA-1 in install/file_attesi.json, insieme alla versione. È il manifest: la lista ufficiale di cosa deve esserci sul server.
3
php tools/pacchetto.php
Prima lancia tools/controlla.php (sintassi di tutti i PHP, nessun file oltre 30 KB, stessa versione in lib.php, novita.php, CHANGELOG e manifest, manifest aggiornato). Se tutto è a posto mette in dist/gesthall-suite-<versione>.zip esattamente i file del manifest più il manifest stesso, e stampa numero di file, dimensione (≈ 1 MB) e SHA-256.
$ php tools/file_attesi.php
198 file in install/file_attesi.json
$ php tools/pacchetto.php
✓ 224 file controllati, versione 3.8.1
dist/gesthall-suite-3.8.1.zip: 199 file, 0.9 MB, sha256 a693b5…
⚠️

Lo zip non contiene mai install/config.php (credenziali del database della sala) né il .htaccess principale: estrarlo o installarlo non può rompere la configurazione. Lo stesso zip serve sia per l'hub sia, se serve, per l'installazione a mano.

03 Pubblicare nell'hub

Hub → Rilasci (solo superadmin) → Carica versione.

  • L'hub apre lo zip, legge install/file_attesi.json e da lì prende il numero di versione: non lo si scrive a mano.
  • Controlla che ogni file del manifest sia nello zip e che ci siano includes/lib.php e la pagina degli aggiornamenti; rifiuta una versione già presente.
  • Salva lo zip in storage/rilasci/ dell'hub (cartella non raggiungibile dal web: .htaccess + regola nel .htaccess principale) e nella tabella rilasci registra versione, nome del file, SHA-256, dimensione, note e stato.
  • Pubblicato = proposto alle sale. Ritira lo nasconde senza cancellarlo (utile se si scopre un problema). Note = testo che il responsabile legge prima di aggiornare: novità, eventuali query SQL.

In Rilasci e nella Dashboard si vede quante installazioni sono ferme a versioni precedenti; nella tabella installazioni la colonna Versione diventa arancione per chi non ha l'ultima e indica da quanti giorni la sala non si collega.

04 Come la sala scopre la nuova versione

Con il controllo della licenza che esisteva già, al quale ora la suite aggiunge la propria versione.

1
Quando parte
Al massimo una volta ogni 24 ore, quando un responsabile apre una pagina dell'app (non i ghost login), oppure subito con Controlla ora nella pagina Aggiornamenti. Non serve nessuna operazione pianificata sul server.
2
La richiesta
GET {hub}/api/license.php?key=CHIAVE_INSTALLAZIONE&v=3.8.0 (timeout 3 secondi: se l'hub non risponde la sala lavora normalmente). La chiave è quella inserita in Impostazioni → Piano e licenza.
3
L'hub risponde
Aggiorna installazioni.versione e ultimo_contatto, poi restituisce piano, scadenza e — se esiste un rilascio pubblicato più recente di v — il campo aggiornamento: versione, SHA-256, dimensione, note, data.
4
La suite lo ricorda
Salva queste informazioni in impostazioni_testi.aggiornamento_cache e la pagina Aggiornamenti mostra «Disponibile la versione …» con le note.
🔑

Senza chiave di installazione la sala non riceve proposte di aggiornamento: può comunque installare un pacchetto con Installa da un file. Con licenza scaduta l'hub rifiuta il download.

05 Installazione e ritorno alla versione precedente

Cosa succede, in ordine, quando il responsabile preme Aggiorna ora (circa un minuto).

#PassoDettaglio
1RequisitiEstensione PHP zip, possibilità di scaricare (cURL), cartelle dell'app scrivibili. Se manca qualcosa la pagina lo spiega e non procede.
2Backup del databaseCopia completa, tipo «Prima dell'aggiornamento» (vedi sezione Backup).
3Download{hub}/api/aggiornamento.php?key=…&v=3.8.1 → account/uploads/aggiornamenti/download_3.8.1.zip. Se lo SHA-256 non coincide con quello ricevuto dall'hub, il file viene cancellato e ci si ferma.
4Verifica del contenutoPer ogni file del manifest: presente nello zip, stessa dimensione, stessa impronta SHA-1, percorso ammesso (mai config.php, .htaccess principale, account/uploads/, niente ..).
5Copia di sicurezzaI file che stanno per cambiare vengono messi in account/uploads/aggiornamenti/precedente_3.8.0_AAAAMMGG_HHMMSS.zip, con l'elenco dei file nuovi (da cancellare in caso di ritorno).
6ScritturaSolo i file diversi: ognuno scritto in nomefile.gh-tmp e poi rinominato, così nessuno resta mai a metà. Un blocco impedisce due aggiornamenti contemporanei.
7Controllo finaleTutti i file confrontati di nuovo con il manifest; cache di PHP svuotata; operazione registrata nell'audit con versione, numero di file, backup e copia.
Tornare indietro

Versioni precedenti → Ripristina rimette i file della copia di sicurezza e cancella quelli aggiunti dall'aggiornamento. Il database non viene toccato: se l'aggiornamento avesse cambiato dati, si usa il backup «Prima dell'aggiornamento» nella pagina Backup. Si conservano le ultime 3 copie.

Installa da un file

Stessa procedura dal passo 4, con lo zip caricato dal browser invece che scaricato dall'hub. Rifiuta una versione più vecchia di quella installata. È l'alternativa all'FTP per le sale senza licenza collegata o quando l'hub non è raggiungibile.

⚠️

Nessuna migrazione automatica del database: le colonne e le tabelle nuove si creano da sole al primo uso; se una versione richiede query, vanno nelle note del rilascio e nel CHANGELOG.

06 Backup del database

Il backup lo fa l'app stessa, in PHP: non usa mysqldump, cron o strumenti di SiteGround, quindi funziona su qualsiasi hosting.

Come viene prodotto
  1. L'app si collega al proprio database con le credenziali di install/config.php (le stesse che usa sempre).
  2. Legge l'elenco delle tabelle (SHOW FULL TABLES) e, per ognuna, la struttura (SHOW CREATE TABLE) e tutte le righe (SELECT *, lette una alla volta per non riempire la memoria).
  3. Scrive un file SQL compresso: per ogni tabella DROP TABLE IF EXISTS, CREATE TABLE … e le righe in blocchi di INSERT (massimo 200 righe o 1 MB per istruzione). Ogni istruzione occupa una sola riga: è il formato che rende possibile il ripristino affidabile.
  4. Prima riga fissa (-- GestHall Suite 3.8.0 — backup del database …) e ultima riga fissa (-- fine backup): servono a riconoscere un file completo. Il file si scrive come .tmp e prende il nome definitivo solo alla fine.

  • Conservazione: gli ultimi 8 (impostabile da 2 a 30), automatici e manuali insieme; i più vecchi vengono cancellati a ogni nuovo backup.
  • Peso: pochi KB per una sala nuova, qualche MB dopo anni (le firme dei versamenti sono la parte più pesante).
  • Non contiene i file caricati (account/uploads/documenti, bordero, lul, chat, foto profilo): per quelli valgono i backup giornalieri di SiteGround o una copia della cartella account/uploads.
  • Impostazioni coinvolte: backup_auto, backup_conserva, backup_ultimo (uniche per l'installazione, anche con più sale).
07 Ripristino
  • Dall'app: Admin → Backup → «Ripristina» su una riga, oppure «Carica e ripristina» con un file .sql.gz; si scrive RIPRISTINA per conferma. L'app controlla prima e ultima riga, salva lo stato attuale e poi esegue il file una riga alla volta.
  • Da phpMyAdmin (se l'app non si apre): SiteGround → Site Tools → MySQL → phpMyAdmin → database della sala → Importa → scegli il .sql.gz. Il formato è SQL standard.
  • Un backup si può ripristinare anche su un'altra installazione (es. per spostare una sala): attenzione che sostituisce tutto, utenti e impostazioni compresi.
⛔

Il ripristino sostituisce l'intero database: le operazioni fatte dopo la data del backup spariscono (restano solo nella copia «Prima del ripristino»). Avvisare la sala prima di farlo.

09 Accesso, avvisi ed export
Blocco dei tentativi

5 errori dallo stesso IP in 15 minuti bloccano quell'IP; 10 errori sullo stesso nome utente, da qualsiasi IP, bloccano l'utente per 15 minuti. Tabella login_attempts (colonna username aggiunta in 3.8).

Verifica in due passaggi

Impostazioni → Sistema (login_2fa). Per responsabili e revisori con email: dopo la password l'utente resta fuori finché non inserisce il codice di 6 cifre ricevuto via email (10 minuti, 5 tentativi, «Invia un nuovo codice» dopo 60 secondi). «Non chiederlo più su questo dispositivo» crea un cookie gh_dev valido 30 giorni (tabella login_dispositivi). All'attivazione vengono revocati i «Resta connesso» di responsabili e revisori; «Dimentica i dispositivi» annulla tutti i dispositivi attendibili. Il ghost login dall'hub non chiede il codice: è la via d'uscita se le email non funzionano.

Avvisi automatici

Ai responsabili della sala, nella campanella e via push: scostamento di cassa oltre soglia al salvataggio di un turno (avviso_scostamento, 20 €), prodotto del bar alla scorta minima (avviso_scorta_bar), ticket aperto oltre avviso_ticket_giorni giorni (3, controllato al massimo ogni 6 ore durante la navigazione). Ogni evento parte una volta sola (tabella avvisi_inviati); ogni responsabile può disattivarli dal profilo.

Export per il commercialista

Cassa → Mensile → «Per il commercialista»: Excel con fogli Riepilogo, Incassi (turno di chiusura, per piattaforma), Versamenti confermati e Bar. Responsabile e revisore.

Promemoria di scadenza

Dai 15 giorni prima della scadenza (e a licenza scaduta) il responsabile vede un avviso con il link a Piano e licenza; si può nascondere per la giornata.

10 Aggiornare a mano (File Manager)

Serve per la prima installazione della 3.8 (che porta il sistema di aggiornamento) o se l'app non si apre.

1
Carica lo zip intero
SiteGround → Site Tools → File Manager → cartella dell'app (quella con index.php, account/, includes/) → Carica gesthall-suite-x.y.z.zip. Meglio dell'FTP: un solo file, nessun troncamento.
2
Estrai
Clic destro sullo zip → Extract → stessa cartella, sovrascrivendo. Poi elimina lo zip.
3
Verifica
Nell'app: Impostazioni → Sistema → Verifica file (confronta ogni file con install/file_attesi.json). Se l'app dà errore 500: copia tools/diagnosi.php nella cartella dell'app, aprilo dal browser, poi cancellalo (si disattiva da solo dopo 24 ore).
📏

Regola dei file piccoli: nessun file dell'app supera 30 KB (l'FTP di SiteGround li troncava a 32 KB). tools/controlla.php e la CI su GitHub bloccano un rilascio che la violi.

11 Checklist di rilascio
1. GH_VERSION in includes/lib.php e includes/novita.php
2. docs/CHANGELOG.md (tecnico, con eventuali SQL)
3. sito: src/data/changelog.json (testo clienti + highlights), pagine e guida se serve
4. GH_TEST_DB=gh_test php tests/run.php
5. php tools/file_attesi.php
6. php tools/pacchetto.php            ← include tools/controlla.php
7. commit + merge su main + push (la CI ripete controlli e test)
8. Hub → Rilasci → Carica versione → note → Pubblica
9. Una sala di prova: Aggiornamenti → Controlla ora → Aggiorna ora → Verifica file
